## Context

The team makes frequent technical decisions about libraries, tooling, patterns, and infrastructure. These decisions are currently communicated through pull requests, Slack messages, or verbal discussions — all of which are ephemeral. When a new team member joins, or when an existing member revisits a decision months later, the rationale is lost. This leads to repeated debate, inconsistent practices, and knowledge silos.

## Decision

We will record significant technical decisions as **Architectural Decision Records (ADRs)** in `docs/adr/`. Each ADR is a short markdown file following a lightweight template:

- **Title** — clear, searchable name
- **Context** — what problem we're solving, what options were considered
- **Decision** — what we chose and why
- **Status** — Accepted, Proposed, Deprecated, Superseded
- **Consequences** — trade-offs, migration effort, follow-up work

## Format

- Files are named `ADR-NNN.md` (zero-padded, e.g. `ADR-001.md`).
- Sequence numbers are monotonic — never reused.
- When a decision is superseded, the new ADR references the old one via `Supersedes:`.

## Consequences

**Positive:**
- Newcomers can learn historical context without interrupting the team.
- Discussions are anchored to a written record, reducing repetitive debate.
- Decisions become auditable — reviewers can see *why* something was done, not just *what* was done.

**Negative:**
- Writing ADRs adds overhead for significant decisions.
- Records can become stale if not maintained.

**Neutral:**
- ADRs can be PR'd and reviewed like code.
- Not every decision needs an ADR; use judgment (e.g., small refactors or bug fixes don't warrant one).
