## Context

The repository currently ships both `package-lock.json` (npm) and `yarn.lock` (Yarn Classic v1), leading to confusion about which package manager to use. The project needs a single, modern package manager that is:

- **Fast on cold installs** — CI pipelines and fresh clones shouldn't take minutes.
- **Disk-efficient** — node_modules should not be bloated.
- **Deterministic** — lockfile guarantees reproducible builds.
- **Secure by default** — postinstall scripts should be auditable.
- **Compatible with this stack** — React 18 + Vite + MUI + TypeScript.

We benchmarked **npm 11**, **Yarn 4 (PnP + node-modules)**, **pnpm 11**, and **Bun 1.3** on this exact repository. Full results: `/tmp/opencode/pm-benchmark/RESULTS.md`.

## Options Considered

### npm 11

- **Pros**: Already bundled with Node.js; minimal learning curve.
- **Cons**: 3m 40s cold install (slowest by far); 657 MB node_modules (largest tied with Bun); serial resolution with poor CPU utilization (113%); no supply-chain security blocking postinstall scripts by default.

### Yarn 4 (PnP)

- **Pros**: Fast (37s); no node_modules (36 MB .yarn/ cache).
- **Cons**: 2.8 GB peak RAM (highest); PnP breaks tooling (TypeScript, ESLint, Jest all need sdks setup); `.yarn/cache/` committed to git bloats history; not compatible with this repo's test/dev toolchain without additional configuration.

### Yarn 4 (node-modules linker)

- **Pros**: Standard node_modules layout; faster than PnP (25s).
- **Cons**: Still 2.3 GB RAM; 596 MB node_modules (17% larger than pnpm); slower than pnpm and Bun; adds Yarn as an extra dependency (not shipped with Node).

### Bun 1.3

- **Pros**: Fastest (9s); lowest RAM (746 MB).
- **Cons**: Not yet universal — no Windows CI parity; no lockfile merge strategy; smaller ecosystem for build tools and plugins; team would need to install and maintain Bun separately. Included for future reference only.

### pnpm 11 (selected) ✓

- **Pros**:
  - 13s cold install (17× faster than npm)
  - 495 MB node_modules (25% smaller than npm/Bun, 17% smaller than Yarn nm)
  - Content-addressable store → deduplication across projects
  - Strict dependency isolation (no phantom deps)
  - Supply-chain security: blocks postinstall scripts by default with explicit `allowBuilds` config
  - Smallest lockfile (268 KB pnpm-lock.yaml)
  - Deterministic via `pnpm-lock.yaml`
- **Cons**:
  - Symlinked node_modules can confuse some tools (not an issue for Vite-based frontend)
  - Shared store can corrupt under rare edge cases (mitigated by `verifyStoreIntegrity`)
  - Team learning curve (but similar CLI to npm: `pnpm install`, `pnpm add`, `pnpm remove`)

## Decision

**Use pnpm 11 as the single package manager.** The existing lockfiles (`package-lock.json`, `yarn.lock`) will be removed. All team members and CI pipelines must use `pnpm install`.

### Enforcement

1. **`"packageManager": "pnpm@11.9.0"`** added to `package.json` — recognized by Corepack, npm ≥9, and pnpm itself.
2. **`"preinstall": "npx only-allow pnpm"`** added to `scripts` — blocks `npm install`, `yarn install`, and `bun install` at the install step with a clear error message. This works across all operating systems without system-level hooks.
3. **`pnpm-workspace.yaml`** at repo root configures `allowBuilds` for the four packages with postinstall scripts that are safe to skip.

## Consequences

**Positive:**
- CI install drops from ~4 minutes (npm) to ~15 seconds.
- Disk usage drops by 25%.
- No more duplicate lockfiles.
- Supply-chain security is enforced by default.

**Negative:**
- All team members must install pnpm (`npm install -g pnpm` or `corepack enable`).
- Existing local node_modules must be deleted and reinstalled.
- CI configuration must switch from `npm install` / `yarn install` to `pnpm install`.

**Migration:**
1. Delete `node_modules/`, `package-lock.json`, `yarn.lock` from all branches.
2. Run `pnpm install` to generate `pnpm-lock.yaml`.
3. Commit `pnpm-lock.yaml` and remove the other lockfiles from `.gitignore` if listed.
4. Update CI scripts and developer onboarding docs.
